PROBLEM
Handing one of these containers a new configuration is supposed to leave it indistinguishable from one that had been created with that configuration from the start. It is not. The re-initialisation path was written once, against the fields that existed then, and every field added since - the per-item defaults, the callbacks the host passes down, the derived slots that were introduced alongside them - is simply not mentioned in it. So the fields the original author listed are replaced and everything else survives from the previous configuration, invisibly, until something reads one of the survivors and behaves according to a configuration the caller has already replaced. The bug is not in any one field: it is that the reset enumerates rather than derives, so it goes stale every time the shape grows, and nothing fails when it does. The contract is that there is exactly one description of what a fresh instance contains and both creation and re-initialisation must be expressed in terms of it. Elsewhere in the folder that is done deliberately: one library demands that every constituent reducer answer the initialisation probe with its own starting value and refuses to assemble the whole if any of them cannot, one gives its state slots an explicit reset-to-initial protocol so a caller never has to enumerate them, and one keeps its default state in a single description that the constructor consumes. Which files re-initialise by enumeration, and which own the single-description contract they have to be brought in line with?
