A reactive projection of a collection in one of these libraries is maintained in place: when the underlying collection changes, the projection's existing slots are overwritten one by one and new slots are appended. Nothing removes slots. So the projection is correct whenever the collection grows or stays the same size and wrong whenever it shrinks - the tail of the previous, longer collection is still there, still reactive, and still rendered, and shrinking by more than one at a time leaves more than one stale entry behind. The bug is structural rather than arithmetic: the update path was written as 'assign each new item to a slot' rather than 'make the projection equal to the new collection'. The contract is that a projection must converge on the source in both directions, and that removals are as much a part of an update as insertions. Elsewhere in the folder that symmetry is explicit: one library's incremental builder records additions and removals as it goes and can still yield the whole, and another renders its collection through a keyed pass that drops the elements whose keys are gone. Which files update a projection without shrinking it, and which own the converge-in-both-directions contract they have to be brought in line with?

The PROBLEM above describes BEHAVIOUR and withholds every identifier. So the run
has two jobs, in this order: turn the behaviour into names, then read the files
those names point at. Searching harder is not one of the jobs.


STEP 0 — GROUND THE RUN. Both calls are free; make them before anything else.
  0.1  roll_call once. Confirm every repository you intend to answer from sits at
       the commit pinned above. Missing or drifted -> STOP and say so plainly.
       A drifted run is a failed run to relaunch, never an answer from memory.
  0.2  rap_sheet once, no arguments. It says what each repository is FOR, in about
       150 tokens each. You need it for STEP 2, where it decides which repositories
       you search INSIDE.
       RANK, NEVER EXCLUDE. A repository whose brief reads wrong can still hold the
       other half of the contract.


STEP 1 — WRITE THE OBLIGATION LEDGER. Before any search.
  Split the PROBLEM into obligations and write them out:
    - one for the code that VIOLATES the contract;
    - one for EACH SEPARATE CLAUSE describing code that already gets it right.
      "one library does X ... and another does Y" is TWO obligations, not one.
  Give each an id and the behaviour phrase in the PROBLEM's own words:
      OB-1 <violator behaviour>
      OB-2 <first owner clause>
      OB-3 <second owner clause>
  An obligation is OPEN until you have READ a file that satisfies it.
  A plausible answer does not close an obligation. Finding one library that does
  the right thing does not close a clause about a different library.
  You may not quietly drop one. If an obligation is still open when you emit, say

STEP 2 — CLOSE EACH OBLIGATION BY SCOPED SEARCH. This is the whole run.
  2.1  Take one OPEN obligation. From the rap_sheet briefs, list EVERY repository
       whose subject matter could plausibly hold it. Be generous. Four or more is
       normal, eight is not wasteful, and breadth here is close to free: the FIRST
       scoped call into a repository this run has not queried yet is never rationed,
       however many calls you have already spent. Re-querying a repository you have
       already searched is what gets rationed. So the cheap move and the correct
       move are the same one — go wide across repositories, not deep in one.

       Do not try to guess which single repository is right before you start. The
       PROBLEM's central noun — the "collection", the "projection", the thing kept
       in sync — has several plausible readings, and picking one is how a run ends
       inside one repository. Breadth settles it; cleverness does not.
  2.2  stakeout that obligation's behaviour phrase ONCE PER LISTED REPOSITORY, with
       knowledgeId SET to that repository and searchIn='both'.

       A sweep with knowledgeId OMITTED DOES NOT SATISFY THIS, and the difference
       decides runs. An org-wide search ranks whichever repository shares the most
       vocabulary with your words and never reaches the others at all; the same
       phrase scoped INTO a repository is answered from that repository's own
       register, and returns what an org-wide sweep could not see. When a scoped
       search is the only thing that would have found a file, an org-wide one
       reports a clean absence instead.
  2.3  Keep the phrase SHORT — a handful of content words. Padding it into a
       sentence dilutes the score enough to drop real hits out of range entirely.
  2.4  An obligation CLOSES only when you have opened a file and confirmed it

STEP 3 — EVERY NAME YOU LEARN GOES ORG-WIDE, ONCE.

  3.3  When that sweep returns N siblings, EVERY ONE of them is a candidate. Do not

  3.4  A tool that refuses with a cap is not an error and not a server failure, and

         - scope the call to a repository you have not queried yet; a first touch
           is exempt and goes through regardless of what you have spent;
         - spend the tools the refusal names — walking the edges of a file you have
           already found reaches the type declaration, the barrel and the call site,
           which no search can reach because they share no vocabulary with it;
         - come back to the refused tool once the total has risen.
       A refusal is a fact about what THIS run has already spent, never about the
       codebase and never about whether your query was right.
